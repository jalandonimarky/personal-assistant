1 · What this is

A local web interface for the Claude Code CLI. It runs on one laptop, is reachable only from that machine, and stores everything in plain files on it. There is no server, no database and no cloud component of its own.

The central design decision is that it owns no model and no conversation state. Every turn shells out to claude -p, which inherits the authentication Claude Code already has and keeps the conversation in its own session storage. The app never resends history — it passes --resume and the CLI handles context, compaction and token budgeting for free.

Consequence worth stating first. Without Claude Code installed and signed in, none of this works — not degraded, not read-only, but not at all. Google, Telegram and documents are all downstream of that one dependency.

Two things flow outward, and only two: prompt content to Anthropic via the CLI, and API calls from whichever MCP servers you have signed in. The app itself makes no external requests — every fetch() in the Next code is a same-origin relative path.

3 · Why MCP for tools that never leave the machine

A reasonable objection: the documents server builds spreadsheets in your Documents folder and touches no network — so why wrap it in a protocol at all?

Because MCP is not about remoteness. It is the only mechanism by which a model gets a tool. If a capability is not exposed as an MCP server, the model cannot call it. Local or not is irrelevant to that.

The alternative is giving the model Bash and letting it run Python itself. That is worse in every direction: it grants arbitrary command execution rather than five named functions with typed arguments, it cannot be scoped to an output directory, and it cannot be granted per turn. A tool surface of doc_create_spreadsheet(filename, sheets) is something you can reason about. A shell is not.

So mcp/documents means "a local capability with a defined, inspectable surface" — the opposite of an internet connection.

All three launchd agents are generated by scripts/install-agents.sh, which derives every absolute path from its own location. Moving the project and re-running that script is the entire migration.

KeepAlive has a consequence: kill on the app or relay just gets it restarted. Use install-agents.sh --uninstall, or launchctl unload.

Every credentialmacOS KeychainNo — never on disk in the repo

Tokens are never written to store.json, never committed, and never passed on argv — argv is visible in the process list. The app holds no credential of its own: Anthropic auth belongs to Claude Code, and each MCP server holds its own refresh token.

store.json is the single point of loss. It is the only copy of your threads and questions. Writes are atomic and locked, but nothing backs it up — that is yours to arrange.

6 · Installing it elsewhere, and what will break

Prerequisites: macOS, Node 18+, and Claude Code installed and on PATH. Then npm install, npm run dev, and open Settings.

The failures below are ordered by how likely they are to be the thing that stops you.

What you seeCauseFix
Blocks all Turns fail immediately; Settings shows "Not installed" Claude Code missing or not on PATH npm i -g @anthropic-ai/claude-code. There is no fallback — the app is a front end for it.
Blocks all "Not signed in" Claude Code installed but unauthenticated Settings → Sign in to Claude. Browser opens, paste the code back. No terminal needed.
Blocks all Nothing works, any OS but macOS Keychain (security), open, lsof and launchd are all macOS-only None. Credential storage, browser launch, port recovery and scheduling would each need a port. See §7.
Silent "No such tool available" for a service you just set up claude mcp add defaults to local scope, binding the server to the directory it ran in — but turns run from a neutral working directory Register with --scope user. The panel now does. claude mcp list will report it Connected either way, which is what makes this one hard to spot.
Confusing Model calls a tool it was not granted, then reports "no access" --allowedTools pre-approves; it does not hide. A same-purpose account connector stays visible and gets picked Already mitigated — the system prompt names the granted tools. Removing duplicate connectors also helps.
Google Bare 400 … malformed, no parameter named OAuth client is a Web application type. The loopback redirect is permitted for Desktop app only Create a Desktop app client. Nothing to fix on the existing one.
Google 403 … API has not been used in project Gmail API / Drive API not enabled. Separate from consent-screen scopes APIs & Services → Library → enable both. Scopes say what you may ask for; the API must exist to answer.

Billing Turn costs become real ANTHROPIC_API_KEY exported in the shell that started the server Unset it and restart. Settings flags this when it detects it.

7 · Portability, stated plainly

This is a macOS application that happens to be written in TypeScript. Four dependencies are not incidental:

DependencyUsed forWhat a port would need
securityEvery credential, in the Keychainlibsecret on Linux, DPAPI on Windows
openLaunching the browser, revealing filesxdg-open / start
launchdApp, relay and daily sweepsystemd units / Task Scheduler
lsofRecovering a held OAuth portss, or netstat parsing

None is hard individually. Together they are a real port, not a config flag — worth knowing before promising the tool to someone on Windows.

8 · The security shape, in one paragraph

The app binds to loopback only and has no login — the binding is the access control, so do not remove -H 127.0.0.1. Read-only modes cannot write: the tool list is enforced by the CLI, not by instruction. Service access is granted per turn and revoked on navigation. Irreversible and outward-facing actions are absent at every level — no send, no delete, no share — and for Gmail that is structural rather than a setting, because gmail.send is never requested at sign-in, so no token can perform it. Everything at rest depends on FileVault, which should be on.
