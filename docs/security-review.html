1 · What this tool is

A local web interface for the Claude Code CLI. It runs on one laptop, is reachable only on that machine’s network, stores everything in plain files on that machine, and has no server, database, or cloud component of its own.

Functionally it does three things: keeps separate conversation threads per topic, stores notes as markdown files on disk, and scans those notes for commitments that have gone quiet.

The framing that matters for review. This tool introduces almost no new external attack surface — it is a user interface over a CLI that is already installed and already authenticated. The real compliance questions are (a) is Claude Code itself approved for use here, and (b) what corporate data is placed within its file scope. Both of those are true with or without this tool. What this tool changes is convenience — it makes it easier to put a lot of notes in one place and keep them there.

What it is not

  • Not a hosted service. Nothing is deployed; there is no server anyone else connects to.
  • Not multi-user. No accounts, no roles, no sharing features.
  • Not integrated with any corporate system — no Salesforce, no SSO, no directory, no email, no ticketing, no database connections.
  • Not a data pipeline. It does not extract, sync, or transmit records from any business system.
  • Not distributed to anyone. Source is in a private repository.

4 · Disclosed risks

Stated plainly, worst first. None of these are theoretical — each was verified in the running application.

Resolved 28 Aug 2026  Listens on all network interfaces with no authentication

As reported 25 Aug. The development server bound to every interface rather than loopback:

node  <pid>  TCP *:4317 (LISTEN)

Combined with the absence of any login, anyone able to reach port 4317 on the same network can read every stored conversation and write files into the knowledge directories. On a coffee-shop or hotel network, that is any other guest.

Remediation: bind to loopback only — next dev -H 127.0.0.1 — so the socket is unreachable from off-machine.

Applied 28 Aug 2026. Both dev and start in package.json now pass -H 127.0.0.1, and the listening socket is bound to 127.0.0.1:4317 rather than *:4317. Verified by request: loopback answers, the same port on the machine’s LAN address refuses the connection.

One consequence worth knowing. An IPv4-only socket plus localhost resolving to ::1 breaks non-browser clients — browsers fall back to IPv4, curl and fetch do not. scripts/pulse.sh and bot/telegram.mjs default to http://127.0.0.1:4317 for that reason; override with PULSE_BASE_URL and PA_BASE_URL.

High  Corporate data may be transmitted to Anthropic

Whatever notes are stored in, or readable from, an assistant’s scope can be read by the model and therefore sent to Anthropic as prompt content. This is the intended function of the tool, not a defect — but it is the substance of the compliance decision.

Handling and retention of that content is governed by the terms of the Claude subscription in use, not by this application. If that subscription is a personal one rather than a corporate agreement, that distinction should be examined closely before any company data is placed in scope.

Medium  Untrusted content is processed by a model with write access

The Ingest feature exists to paste external material — meeting notes, email threads, vendor decks — into a session whose tools include Write and Edit, with --permission-mode acceptEdits, meaning file writes are not individually confirmed. Pasted content is untrusted input and is a prompt-injection surface.

Existing mitigation: writes are confined to the assistant’s own directory; paths are resolved and rejected if they escape it. The blast radius of a successful injection is corruption of that assistant’s own notes, not arbitrary filesystem access. No shell tool is granted in any mode.

Medium  Mailbox content can be placed in scope, deliberately

The tool can be granted read access to Gmail for an individual turn. When granted, the model can search and read mail, and whatever it reads becomes conversation content — which means it is transmitted to Anthropic like any other prompt content.

Controls in place:

  • Off by default. The grant is ephemeral UI state, never persisted, and is revoked automatically on switching thread, assistant, or tab, and on reload.
  • Read-only by construction. Only five retrieval tools are unlocked. Sending, replying, forwarding, drafting, trashing, labelling and spam-marking are excluded from the list and therefore uncallable — a model acting on a misread email cannot un-send it.
  • Enforced by the process, not by instruction. Access is granted through --allowedTools. Verified: with the application’s normal tool list, a direct instruction to read Gmail returns a refusal, despite the connector being authenticated at the account level.
  • Server-side validation. Service identifiers arrive from the browser and are resolved against a fixed registry; nothing client-supplied reaches the tool whitelist verbatim.
  • Informed grant. The first grant on a given browser requires confirming a dialog that states what is unlocked, what is withheld, and that content reaches Anthropic.
The residual risk is judgement, not mechanism. Nothing prevents a user from granting access and then asking a question that pulls confidential mail into a prompt. This belongs in usage policy — the same boundary discussion as §4’s second finding, now applying to a mailbox rather than a notes folder.

Medium  Plaintext at rest, no application-level encryption

Conversations and notes are readable files. Confidentiality depends entirely on OS disk encryption and account security — FileVault should be confirmed enabled. Claude Code separately retains conversation transcripts under ~/.claude/projects/, which grows without bound.

Low  No audit log, retention policy, or DLP

There is no record of who accessed what, no automatic expiry, and no content inspection. For a single-user local tool this is proportionate, but it means the tool cannot evidence compliance with a retention or access-review requirement.

5 · Controls that do exist

ControlImplementation
Tool whitelistingEach mode passes an explicit --allowedTools list. Read-only modes receive Read · Glob · Grep only. No mode grants shell or command execution.
Directory scopingThe model sees only directories explicitly passed as --add-dir. It is not given the filesystem.
Write confinementEach assistant has exactly one writable directory. Reference directories are read-only by construction. Path traversal is resolved and refused.
Per-turn service grantsExternal service access is off by default, granted explicitly, read-first, and revoked on navigation. Verified as enforced by the CLI rather than by prompt.
No secret handlingThe tool stores no credentials of any kind and never prompts for an API key.
Inspectable stateAll data is human-readable JSON and markdown, available for review or deletion at any time. Deleting data/store.json resets the tool.
Source controlPrivate repository. Conversations, notes, and internal documents are excluded by .gitignore and verified absent from the published tree.

6 · Questions review will likely ask

QuestionAnswer
Where is data stored?Local disk only. No cloud storage, no database, no backup service.
What leaves the machine?Prompt content and the contents of files the model reads within its scope — sent by the Claude Code CLI to Anthropic. The application itself makes no external calls.
Who else can access it?Nobody by design. See the High finding in §4 — the current network binding must be corrected for that answer to hold.
Is customer or regulated data involved?Not by design and not currently. The tool holds working notes. Whether it stays that way is a usage-policy decision, not a technical control.
Is there a vendor to assess?Only Anthropic, and only as the existing provider of Claude Code. This tool adds no new vendor, subprocessor, or data-sharing relationship.
Can it be removed?Entirely. Stop the process and delete the directory. Nothing is installed system-wide and nothing persists elsewhere except Claude Code’s own session files.
Who wrote it?Internally, by the user, for personal use. No third-party code beyond standard open-source npm packages (Next.js, React, markdown rendering).

7 · Recommended before continued use

  1. Bind to loopback. next dev -H 127.0.0.1. Closes the High network finding outright. — Done 28 Aug 2026.
  2. Confirm the Claude subscription’s terms cover company data — corporate agreement versus personal plan. This determines whether §4’s second finding is acceptable or blocking.
  3. Confirm FileVault is enabled on the machine.
  4. Agree an explicit data-class boundary — what may and may not be placed in an assistant’s scope. A written line is easier to hold to than judgement in the moment.
  5. Include connected services in the data-class boundary — Gmail read access is available per turn, so the policy should say plainly which mail may be brought into a prompt.
  6. Decide a retention position for ~/.claude/projects/, which grows without limit and is outside this tool’s control.
Note on scope of this document. It describes the application only. It does not assess Claude Code itself, the Anthropic service, or the terms of the subscription in use — those sit above this tool and should be reviewed on their own terms.
